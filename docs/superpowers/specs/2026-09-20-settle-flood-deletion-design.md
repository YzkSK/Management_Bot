# 連投検知後の投稿収束待ち設計

## 目的

連投 (`flood`) または内容重複 (`duplicate_content`) を検知した直後にも、同じ投稿者が数件送信すると削除対象から漏れる。投稿が収束した時点で、検知の元になった投稿と後続の同一バーストをまとめて削除する。

Dashboard 設定・DB 設定は追加しない。

## 対象としないもの

- NG ワード、メンションスパム、招待リンク、外部リンクなどの単発違反
- 別の投稿者、別チャンネル、別ギルドの投稿
- 既存の検知閾値・エスカレーション段階・処罰内容の変更

## 方針

`handleMessageCreate` に、`guildId`・`channelId`・`userId` 単位の短命な収束待ちコレクターを置く。

1. `flood` または `duplicate_content` の初回検知で、従来と同じモデレーションケースとアクション内容を決定する。ただし Discord API の削除・警告・処罰はまだ実行しない。
2. コレクターを登録し、同一投稿者・同一チャンネルの新規メッセージを収集する。通常の検知フローも継続するが、既存の strike ロックにより同じバーストへの追加処罰は行わない。
3. 初回検知または新規投稿のたびに 1 秒の無投稿タイマーをリセットする。1 秒間の無投稿で収束とみなし、検知時点のバッファと収集済みの後続投稿を同じモデレーションケースへ関連付けて一括削除し、決定済みアクションを実行する。
4. 収束前に後続投稿数が、その検知に使った既存プリセットの `messageThreshold` に達した場合は待機を打ち切る。この時点で収集済みの全投稿に対して、従来と同じアクションと削除を直ちに実行する。

収束待ちは最大でも「1 秒の無投稿」または「既存の投稿件数閾値に達するまで」の短い期間である。後続投稿が続く場合は従来と同じ閾値で即時に処理する。

## ログと削除の整合性

削除直前に、初回検知で作成済みの `caseId` と全メッセージ ID の関連付けを永続化する。これにより `messageDeleteBulk` のログは既存ケースへ紐付き、削除件数・折りたたみ表示が初回分と後続分で分断されない。

収束待ちによる後続削除は追加の strike、追加のモデレーションケース、追加の処罰を発生させない。通常の検知フローは維持するが、既存の strike ロックにより同一バーストでの重複処罰は防ぐ。

## エラー処理と終了条件

- Discord の削除または関連付け書き込みに失敗しても、既存の初回アクション結果を覆さない。失敗はエラーログとして記録する。
- 収束・件数上限・削除失敗のいずれでもコレクターを必ず破棄する。
- 収束待ちの対象が 1 件だけなら既存の個別削除を使い、2〜100 件なら既存の `bulkDelete` を使う。

## テスト

- 検知後に追加されたメッセージを、1 秒の無投稿後に検知時点の投稿と同じケースへ関連付けて削除する。
- 追加投稿数が `messageThreshold` に達すると、無投稿タイマーを待たずに削除する。
- 別の投稿者・別チャンネルのメッセージはコレクターに含めない。
- 後続削除で追加の action イベントや処罰が発生しない。
- 関連付けまたは削除の失敗後にもコレクターが残らない。
