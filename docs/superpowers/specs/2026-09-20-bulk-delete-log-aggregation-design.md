# 一括メッセージ削除ログ集約 設計

## 目的

`messageDeleteBulk` で削除されたメッセージを、削除対象ごとではなく操作ごとに一件のログとして保存する。Dashboard の一覧には中立な要約を一行だけ表示し、展開表示では削除された各メッセージの投稿者と本文を確認できるようにする。

## 対象範囲

- モデレーション自動削除、手動削除、他ボットによる削除を含む、すべての `messageDeleteBulk` イベント。
- Discord Gateway から実行者を確実に取得できないため、一覧文言では実行者を推測しない。
- 既存のモデレーションケースはそのまま残し、自動処理の理由・文脈をそこで確認できる。

単一メッセージの削除イベント、監査ログとの相関方法、既存ログのデータ移行は変更しない。

## データモデル

新しい一括削除ログは `category: "message"`、`action: "bulkDelete"` とし、個別メッセージの `authorId` や `content` はトップレベルに置かない。代わりに、削除前スナップショットを `deletedMessages` に保持する。

```ts
{
  category: "message",
  action: "bulkDelete",
  guildId: string,
  channelId: string,
  createdAt: string,
  deletedMessages: [
    {
      messageId?: string,
      authorId: string,
      authorName?: string,
      content?: string,
      attachments?: MessageAttachment[],
    },
  ],
}
```

件数は `deletedMessages.length` から算出する。メッセージの本文が空でも、投稿者・ID・添付ファイルを含む削除スナップショットは保持する。従来の一件ずつ保存された `bulkDelete` 形式もスキーマで受理し、履歴を壊さない。

## 処理フロー

1. `messageDeleteBulk` ハンドラーは、既存どおりボット自身のメッセージを除外する。
2. 残ったメッセージを `deletedMessages` に変換し、一件の一括削除ログを作る。
3. 一件だけを永続化し、Discord のログチャンネルにも一件だけ要約通知する。
4. Dashboard は新形式を展開すると、スナップショットを投稿単位で表示する。投稿者名がスナップショットにない場合は ID を表示する。最大100件の一括削除が同一ページに複数あっても、表示名解決 API の100件上限を超えないよう、追加の名前解決リクエストには依存しない。

## 表示

一覧と通知の要約は、たとえば `#一般 で 10件のメッセージが一括削除されました` とする。これは実行者を断定せず、「自分の複数のメッセージを削除しました」という誤表示を防ぐ。

Dashboard の展開領域は、各削除対象について次を読みやすい形で表示する。

- 投稿者名（利用できない場合はユーザー ID）
- 本文（空なら本文なしであること）
- 添付ファイル
- メッセージ ID

これらは通常のメッセージログの本文と同じ閲覧権限で表示する。生データ閲覧権限を追加で要求しない。

## 互換性と失敗時の扱い

既存の `bulkDelete` ログは従来の個別メッセージ形式として表示可能なままにする。ただし文言は実行者を示さない中立表現にする。新しい一括ログで削除メッセージを一件も取得できない場合は、ログも通知も作成しない。添付ファイルや本文が欠けていても、取得できたスナップショットは保存・表示する。

## テスト

- 新旧の `bulkDelete` ペイロードをスキーマで検証する。
- 複数の削除メッセージから一件の集約ログを作り、投稿者・本文・添付情報を保持することを確認する。
- 永続化と通知が一括操作あたり一回であることを確認する。
- 新形式と旧形式の要約文言が、実行者を推測しないことを確認する。
- Dashboard の展開表示で投稿者と本文を確認でき、本文なしの状態も分かることを確認する。
