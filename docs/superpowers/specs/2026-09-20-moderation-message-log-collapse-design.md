# モデレーション一括削除の投稿ログ折りたたみ設計

## 目的

モデレーションの一括削除後に削除対象の `message/create` ログが一覧を占有しないようにする。一方で、投稿ログを削除・書き換えず、必要なときに投稿者・本文・添付を確認できる状態を保つ。

## 対象範囲

- 集約形式の `message/bulkDelete` ログに含まれる `deletedMessages[].messageId` と一致する `message/create` ログを対象にする。
- 今後の `message/create` ログにはDiscordメッセージIDを保存する。既存履歴にはIDがないため、本文・投稿者・時刻による推測は行わず通常表示のまま残す。
- Dashboardのログ一覧だけを変更する。
- 旧形式の `bulkDelete`、単発の `message/delete`、永続済みログpayloadは変更しない。

## 表示とAPI

1. ログ一覧APIは、永続レコードとは別の表示用ログ行を返す。
2. `bulkDelete` の対象メッセージIDに一致する `message/create` ログをDB全体から取得し、その一括削除行の `collapsedEntries` として返す。
3. 子に関連付いた投稿ログは通常行から除外する。次ページでも同じログを再表示しない。
4. ページサイズとカーソルは親となる表示行を基準に維持する。子ログはページ件数に含めない。
5. Dashboardは親の直後に「削除された投稿ログ N件」の小さな行を表示し、初期状態では閉じる。展開時に既存ログ詳細と同じ情報を表示する。

## データ取得

- メッセージ作成ハンドラーは、以後の相関用に `messageId` をpayloadへ保存する。
- 一覧の主クエリは既存の `(createdAt, id)` 降順カーソルを維持する。
- `message/create` のうち、集約形式の `bulkDelete` が同じ `messageId` を参照するものを表示対象から除く。
- 各返却対象の `bulkDelete` について、関連する `message/create` を追加取得する。これにより、関連投稿が主クエリの次ページにあっても親の折りたたみへ含められる。
- 関連ログが保持期限などにより存在しない場合でも、一括削除ログは通常どおり表示する。折りたたみ行の件数は実際に取得できた投稿ログ数とする。
- `messageId` を持たない既存の投稿ログは関連候補にしないため、誤った投稿ログを畳まない。

## 権限と互換性

- `VIEW_LOGS_RAW` がない利用者には、既存一覧行と同じ `maskSensitiveFields` を子ログにも適用する。
- カテゴリが `message` または未指定のときだけ集約を行う。他カテゴリ絞り込みの結果は変更しない。
- APIの既存 `entries` は維持し、子ログは明示的な任意フィールドで追加する。

## テスト

- 15件以上の投稿ログが、親の一括削除行へ1グループとして付く。
- 新規の投稿ログに `messageId` が保存され、IDなしの既存投稿ログは通常行に残る。
- 次ページで子ログが通常行として再表示されない。
- 一覧のカーソル・件数・カテゴリ絞り込みを維持する。
- Dashboardの初期折りたたみと、展開後の投稿者・本文・添付表示を確認する。
- 子ログにも機微情報マスキングが適用されることを確認する。
